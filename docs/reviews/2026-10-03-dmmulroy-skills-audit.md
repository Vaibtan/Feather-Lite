## Anti-slop compatibility and cost

The upstream README describes anti-slop as an opinionated ruleset to vendor and customize, with no official npm package. The current installer copies its plugin and provenance, requires `oxlint` and `@oxlint/plugins` at exactly matching versions, wires configuration and agent-folder ignores, and enables 18 generic rules plus the native Oxlint companion rule by default. Because Feather-Lite declares Effect directly, that installer also opts into five Effect rules. This means a fresh install adds a lint stack and policy surface, rather than just adding an instruction file. [README](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/README.md), [installer skill](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/skills/install-anti-slop/SKILL.md), [upstream package pins](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/package.json).

I followed the `find-docs` skill at `C:\Users\hp\.agents\skills\find-docs\SKILL.md` for this library-specific configuration check: Context7 resolved the official Oxlint usage docs, which say JavaScript plugins are currently **alpha** and not covered by semantic versioning. That adds upgrade and maintenance risk to an otherwise useful custom-rule set. [Official Oxlint JavaScript plugins documentation](https://oxc.rs/docs/guide/usage/linter/js-plugins.html)

A quick source scan shows why enabling every rule at `error` would be noisy. These are examples of relevant code, not measured Oxlint diagnostics:

- `no-unknown-parameters` and `no-runtime-typeof` conflict with intentional boundary handling such as [`decodeJudgeVerdict(raw: unknown)`](../../packages/domain/src/judge.ts#L71), [`validateReport(report: unknown)`](../../apps/load-test/src/resources.ts#L960), and SDK event parsing. The same upstream coding standard explicitly recommends parsing unknown external input into domain types, so the lint rule can oppose the documented design unless parser-specific exceptions are defined.
- `no-manual-tag-comparison` is broader than Effect error dispatch in the README. Existing code checks Effect `Either`/`Option` and protocol tags, for example [`parsed._tag === "Right"`](../../apps/voice-worker/src/control-plane-client.ts#L90), as well as ordinary stream-event tags. These need review before blanket enforcement.
- `no-array-filter-map` would touch ordinary pipelines in production and tests, including [outbox transcript projection](../../packages/control-plane/src/services/Outbox.ts#L132) and [load-test event summaries](../../apps/load-test/src/tier1.ts#L542). The upstream docs correctly warn that callback order, sparse-array behavior, and runtime support must be checked; do not mechanically convert them to iterator helpers.
- `no-module-mocking` looks low-cost here: the initial scan found no `vi.mock`/`vi.doMock`/`unstable_mockModule` calls. A chained-cast rule would still need a baseline decision; the test tree contains at least one `null as unknown as` cast ([example](../../apps/voice-worker/test/silenceClock.test.ts#L24)).

The rules use AST and lexical-scope analysis, not TypeScript type checking, and upstream documents limits on cross-file inference and on Effect service-import detection through package aliases. They can prevent specific patterns, but they cannot certify the types or architecture of this code. [Analysis boundaries and Effect rules](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/README.md).

## Minimal integration recommendation

1. Add one focused Effect service-design skill that points to `codebase-design` for vocabulary and requires checking the locked Effect version and local examples. Keep service audits explicit; do not run a whole-repository inventory for routine feature work.
2. Put only a few compatible TypeScript/Effect rules in one concise project reference. Avoid duplicating the general testing, module-depth, and domain-model guidance already present.
3. If the user elects to establish linting, first vendor the plugin at a recorded upstream commit in an isolated branch, run it once to collect the baseline, and review each rule against existing APIs. Start by evaluating the low-conflict `no-module-mocking` rule and selected Effect rules; exclude or customize `no-unknown-parameters`, `no-runtime-typeof`, broad tag matching, and readability formatting unless the baseline supports them. Pin Oxlint and its plugin package exactly together, preserve the upstream license and provenance, and make the new lint script part of checks only after the baseline is accepted.
